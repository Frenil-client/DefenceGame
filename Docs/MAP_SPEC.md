## 1. 왜 루프인가

한국 유즈맵 디펜스 장르의 표준 형태다. 적이 지형을 빙글빙글 돌고, 처리하지 못하면 쌓이고, 일정 수 이상 쌓이면 패배한다.

경로형 대비 이점:

- **목적지 판정, 누출 처리, 본진 방어 개념이 전부 사라진다.** 코드가 줄어든다
- 배치의 의미가 하나로 통일된다. 사거리로 루프를 얼마나 커버하는가
- 랜덤 생성이 쉽다. 폐곡선 하나만 만들면 된다
- 맵 크기가 고정 범위에 묶이므로 카메라 고정을 유지할 수 있다

## 2. 맵 데이터 구조

```
LoopMap
  seed                생성 시드
  gridWidth           16
  gridHeight          12
  tileGrid            셀별 타입 (EMPTY / PATH / BUILD)
  loopWaypointList    루프 순회 웨이포인트 (닫힌 순환)
  buildTileList       배치 가능 타일 목록
  spawnIndexList      스폰 위치 (loopWaypointList 인덱스)
  cornerIndexList     코너 위치 (핫스팟 표시용)
  perimeter           둘레 타일 수
  buildArea           배치 가능 타일 수
  coverageIndex       커버 효율 지수
```

몬스터 위치는 `웨이포인트 인덱스 + 구간 진행도(Fixed)`로 표현한다. 마지막 인덱스 다음은 0으로 돌아간다. 예외 처리가 이 한 줄뿐이다.

## 3. 생성 알고리즘

### 3-1. 왜 요철 방식인가

랜덤 워크로 폐곡선을 만들면 자기교차 처리가 복잡하고 둘레 길이가 통제되지 않는다. 둘레는 곧 한 바퀴 도는 시간이고 그것이 처리 기회 횟수를 결정하므로, 통제되지 않으면 난이도가 런마다 제멋대로가 된다.

기본 링에서 시작해 요철을 넣는 방식은 **위상이 구조적으로 보장된다.** 한 변의 연속 구간을 수직으로 밀어내는 연산은 폐곡선을 유지하며 자기교차를 만들 수 없다. 둘레 변화량도 정확히 예측된다.

### 3-2. 단계

**STEP 1. 기본 링**

- 그리드 16x12에서 안쪽으로 baseRingInset(2)만큼 들어간 직사각형 링을 그린다
- 기본 둘레 = 2 * ((16 - 2*2 - 1) + (12 - 2*2 - 1)) = 2 * (11 + 7) = 36

**STEP 2. 요철 적용**

bumpCount회 반복한다.

1. 네 변 중 하나를 랜덤 선택
2. 그 변에서 연속 구간 [a, b]를 랜덤 선택 (길이 2 이상)
3. 밀어낼 방향(바깥 또는 안쪽)과 거리 d(1 또는 2)를 랜덤 선택
4. 밀어낸 결과가 유효한지 즉시 검사한다
   - 그리드 경계를 벗어나지 않는가
   - 다른 변과의 간격이 minLaneGap(2) 이상 유지되는가
   - 내부 배치 면적이 areaMin 아래로 떨어지지 않는가
5. 유효하지 않으면 그 요철을 버리고 다음으로

한 번의 요철로 둘레가 2d 늘거나 준다. 코너는 4개 추가된다.

**STEP 3. 배치 영역 확정**

- 경로(PATH) 셀을 뺀 그리드의 모든 셀을 BUILD로 표시한다. 루프 안팎 모두 배치 가능하다
- 몬스터 경로 라인 밖에도 유닛을 놓을 수 있어 배치 선택지가 넓어진다
- 단, 형태 지표(MAP-03 내부 면적, 커버 지수)는 루프 내부 기준으로 계산해 맵끼리 비교 가능하게 유지한다

**STEP 4. 스폰 배치**

- loopWaypointList를 spawnCount(3)등분한 지점에 배치한다
- 균등 배치이므로 랜덤 요소는 없다. 요철 때문에 실제 위치는 맵마다 달라진다

**STEP 5. 검증**

4장의 제약을 전부 통과해야 한다. 실패하면 시드를 증가시켜 재생성한다. maxRetry(30)회 실패하면 폴백 템플릿 맵을 반환한다.

## 4. 제약 조건

린터와 생성기가 같은 코드를 공유한다.

| ID | 항목 | 범위 |
|---|---|---|
| MAP-01 | 둘레 길이 | 44 - 56 타일 |
| MAP-02 | 코너 수 | 8 - 16 |
| MAP-03 | 내부 배치 면적 | 30 - 50 타일 |
| MAP-04 | 서로 다른 변 사이 최소 간격 | 2칸 이상 |
| MAP-05 | 커버 효율 지수 | 목표 범위 내 (5장) |
| MAP-06 | 커버 0인 배치 타일 비율 | 5% 미만 |
| MAP-07 | 자기교차 | 없음 (구조적으로 보장, 회귀 테스트로만 확인) |

MAP-04가 없으면 루프의 두 변이 딱 붙어 유닛 하나가 양쪽을 동시에 때리는 과도한 핫스팟이 생긴다.

MAP-06이 없으면 내부에 아무도 쓸모없는 죽은 공간이 생긴다.

## 5. 커버 효율 지수

루프형에서 맵 난이도는 형태가 아니라 커버 효율로 결정된다.

```
각 배치 타일 t 에 대해:
    cover(t) = 사거리 R 안에 들어오는 루프 타일 수

coverageIndex = buildTileList 전체의 cover(t) 평균
```

R은 기준 사거리(레어 등급 원거리 유닛의 사거리)를 쓴다. 실제 유닛 사거리는 다양하지만 지수는 하나의 기준으로 통일해야 맵끼리 비교가 된다.

- 코너가 많으면 지수가 높다. 코너 안쪽 한 자리가 두 변을 동시에 때린다
- 직선이 길면 지수가 낮다
- 따라서 **코너 수와 둘레를 함께 제어해 지수를 일정 범위로 유지**해야 한다

목표 범위는 시뮬레이터로 확정한다. 초기값은 임시로 둔다.

## 7. 결정성

- 생성기는 Core에 둔다. Unity 없이 dotnet에서 돌아가야 한다
- DeterministicRandom을 주입받는다. 같은 시드는 항상 같은 맵을 낸다
- 난수 소비 순서가 곧 결과다. 요철 적용 순서를 바꾸는 리팩터링은 맵을 바꾼다
- 생성 결과를 해시로 검증하는 테스트를 STEP 1부터 유지한다

---

## 8. 랜덤화의 실질적 가치

형태가 예뻐지는 것이 목적이 아니다. **코너 핫스팟과 스폰 위치가 매 런 달라지는 것**이 목적이다.

- 같은 유닛 구성, 같은 히어로라도 배치 최적해가 달라진다
- 히어로 오라 반경과 코너 핫스팟의 교집합을 매번 새로 찾아야 한다
- 합성 시스템의 재플레이 가치가 맵 변수와 곱해진다

따라서 생성기의 성공 기준은 "맵이 다양해 보이는가"가 아니라 **"맵에 따라 최적 배치가 실제로 달라지는가"**이다. SIM으로 검증한다.

## 9. 구현 구조

```

  BumpOperation.cs         요철 연산 하나
  LoopMapValidator.cs      MAP-01 부터 MAP-07 검증

```

Tools/Linter는 LoopMapValidator를 그대로 호출한다. 검증 로직을 두 벌 만들지 않는다.

## 10. 시각 처리 메모

상세는 STEP 8에서 정한다. 현재 확정된 것만 적는다.

- 배치 타일은 지면보다 올린다. 높이차와 그림자로 놓을 수 있는 칸이 읽힌다
- 격자는 평소 은은한 테두리만, 유닛을 집어들면 배치 가능 칸이 발광한다
- 코너 핫스팟은 별도 표시하지 않는다. 플레이어가 찾아내는 것이 재미다
- 순회 몬스터는 GPU 인스턴싱으로 그린다. 동시 60기가 상한이다
- 루프 경로 위에 스크롤 UV 이미시브를 얹어 흐름 방향을 보여준다
